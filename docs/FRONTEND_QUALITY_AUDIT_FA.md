## ۲) واقعیت معماری فعلی

- Preview/PWAها از HTML پوسته و JavaScript/CSS مشترک Vanilla استفاده می‌کنند؛ سورس اصلی در `shared/src/` است و خروجی با `shared/build.js` ساخته می‌شود.
- فرانت‌اند متصل به بک‌اند از Django Templates و فایل‌های استاتیک `django/templates/` و `django/static/` استفاده می‌کند.
- بک‌اند فعلی Django از `accounts`، `coaches` و `store` تشکیل شده است. ادغام قالب‌های پیشنهادی در CI، صرفاً در checkout موقت و جدا از مخزن بک‌اند انجام می‌شود.
- در سند فاز ۱ به React/Tailwind v4 و الگوی کامپوننت اشاره شده، اما تسک‌های ۷ نوامبر روش تحویل مستقیم HTML/CSS/JS به `templates/` و `static/` را مشخص می‌کنند. پیاده‌سازی جاری بر مبنای معماری دوم است؛ مهاجرت React انجام نشده و بدون تصمیم صریح کارفرما نباید ناگهانی شروع شود.

## ۵) اصلاحات کیفیتی این بازبینی

این بازبینی در شاخهٔ جدا و با PR #16 انجام می‌شود:
- رفع خطای runtime در قالب‌بندی عددهای Django: استفادهٔ اشتباه از querySelector تک‌عنصری به‌جای مجموعهٔ عناصر اصلاح شد.
- اصلاح عبارت منظم جداکنندهٔ هزارگان تا comma فارسی/لاتین و فاصله را از رشتهٔ عددی حذف کند.
- افزودن تست مرورگری برای حالت بدون عدد، چند عدد، جداکنندهٔ فاصله/کاما، toast پیام جم و فوکوس خطای سرور.
- اجرای suite کامل مرورگری سه PWA و پنل مارکتینگ در CI؛ قبلاً فقط دو مجموعهٔ متمرکز clubs و Preview اجرا می‌شد.
- افزودن آزمون مرورگری مستقل برای تراز کارت و CTA در فروشگاه، ویدیو، مربیان و دوره‌ها روی دسکتاپ و بررسی overflow در موبایل.
- اجرای آزمون runtime جاوااسکریپت Django در workflow مرورگری و افزودن مسیر `django/static/js/**` به trigger آن.
- محافظت از CSS تولیدی Django در pushهای main و PRهای fork: خروجی تولیدی در مواردی که CI امکان commit-back ندارد، با سورس مقایسه می‌شود.
- اصلاح checkout workflow برای استفاده از repository/ref واقعی PR در سناریوی fork.

هیچ فایل Python، migration، مدل، view، URL، تنظیمات یا دیتابیس بک‌اند در این بازبینی تغییر نمی‌کند.

## ۶) معیار خروج و محدودیت‌های تأیید

- `node --check` فقط syntax را بررسی می‌کند؛ تست مرورگری runtime برای سناریوهای مشخص لازم است.
- اجرای `manage.py check` و ۱۸ تست موجود بک‌اند در checkout موقت، سازگاری پایهٔ قالب‌های Django با snapshot مشخص بک‌اند را نشان می‌دهد، نه صحت عملیاتی در هاست تولید.
- تست‌های مرورگری PWAها داده‌های نمونه/Mock را نیز پوشش می‌دهند؛ این تست‌ها اتصال واقعی بانک اطلاعاتی یا پرداخت را ثابت نمی‌کنند.
- CI ساخت Preview با موفقیت artifact تولید می‌کند، اما در آخرین اجرای main، Secretهای `FTP_SERVER`، `FTP_USERNAME` و `FTP_PASSWORD` خالی بوده‌اند؛ مراحل دانلود و FTPS deploy اجرا نشده‌اند. بنابراین Preview روی cPanel به‌روزرسانی‌شده محسوب نمی‌شود.
- Build گزارش کرده `local fonts: 0` و `TP_API_BASE: (unset)`; برای هر محیط انتشار باید تنظیمات مربوطه جداگانه تعیین شوند.

## ۷) کارهای بعدی که واقعاً به فرانت‌اند مستقل مربوط‌اند

1. تکمیل Admin UI فقط پس از دریافت قرارداد URL/JSON و تأیید مجوز override کردن قالب Admin؛ بخش unread به endpoint بک‌اند نیاز دارد.
2. دریافت فایل‌های مجاز WOFF2 و جایگزینی Google Fonts، همراه با به‌روزرسانی build و preload.
3. تکمیل تست‌های بصری screenshot-based برای صفحات کلیدی پس از ثابت شدن محتوا و مسیرهای نمونه.
4. تعیین تکلیف معماری React/Tailwind در برابر Django templates؛ این تصمیم قبل از هر مهاجرت ساختاری باید از کارفرما گرفته شود.
5. ادغام/تحویل مستقل PR #4 فقط پس از قرارداد backend یا تصویب نسخهٔ صرفاً نمایشی؛ PR #5 قبل از هر استفاده باید مشکلات review برطرف و با قرارداد واقعی Gems تطبیق داده شود.

**نتیجه:** کیفیت و پوشش تست فرانت‌اند موجود بهبود یافته، ولی فاز ۱ کارفرما به‌طور کامل تحویل نشده است. OTP، نقش باشگاه، checkout/payment، دوره‌های واقعی، جم واقعی و endpointهای نقشه/HTMX هنوز به توسعه یا تصمیم بک‌اند نیاز دارند.
