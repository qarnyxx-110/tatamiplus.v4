# کاتالوگ اجزای رابط تاتامی پلاس

**وضعیت:** قرارداد طراحی نسخهٔ ۰.۱، استخراج‌شده از Design System و CSS فعلی  
**منبع توکن:** `shared/src/design/tokens.json`  
**منبع استایل:** `shared/src/css/` و استایل Django از `shared/src/css/django.css`  
**قاعده:** این سند بین «جزء موجود» و «جزء پیشنهادی برای استانداردسازی» تفاوت می‌گذارد. وجود نام در این فهرست به معنی وجود پیاده‌سازی کامل در تمام صفحات نیست.

## ۱. اصول مشترک

- RTL و متن فارسی حالت پیش‌فرض است؛ متن لاتین، کد، شماره و شناسه با `bdi` یا `.tp-ltr` ایزوله شود.
- رنگ برند قرمز تاتامی است؛ طلایی برای تأکید. آبی جودو فقط برای معناهای مستقل مانند کمربند آبی و نشانه‌های فنی AI باقی می‌ماند.
- یک CTA اصلی در هر قاب بصری؛ دکمهٔ کپسولی استفاده نشود.
- اندازهٔ هدف تعاملی ترجیحاً حداقل ۴۴×۴۴ پیکسل باشد. این یک معیار طراحی محصول است؛ جایگزین بررسی WCAG برای فاصله‌گذاری و دسترس‌پذیری نیست.
- هیچ وضعیت موفق، مبلغ، موجودی، شمارنده یا نتیجهٔ مالی فقط با تغییر ظاهری کلاینت معتبر نمی‌شود.
- کلاس‌های جدید با پیشوند `tp-` نام‌گذاری شوند. کلاس‌های کوتاه فعلی فقط برای سازگاری حفظ و به‌تدریج مهاجرت داده شوند.
- حرکت فقط برای بازخورد و جهت‌دهی؛ با `prefers-reduced-motion` حذف شود.

## ۲. اجزای موجود

| شناسه | جزء | پیاده‌سازی فعلی | کاربرد | وضعیت‌ها/نکته |
|---|---|---|---|---|
| C-01 | دکمه | `.btn`، `.btn.o`، `.btn.s`، `.btn.dg` | CTA، اقدام ثانویه، کوچک، تخریبی | hover، active، disabled؛ loading باید با وضعیت واقعی کنترل شود |
| C-02 | چیپ/فیلتر | `.chip` | انتخاب دسته، فیلتر، کنترل انتخابی | عادی، hover، selected با `aria-pressed` یا `aria-selected`، disabled |
| C-03 | برچسب وضعیت | `.tag` و گونه‌های `.g`، `.m`، `.danger`، `.ok`، `.lo` | وضعیت منتشرشده، اطلاع، خطا، موفق، هشدار | متن وضعیت الزامی؛ رنگ به‌تنهایی کافی نیست |
| C-04 | کارت | `.card`، `.d-c`، گونه‌های feature مانند `.pcd` و `.rec` | نمایش آیتم، دوره، محصول، محتوا | لینک‌دار یا ایستا؛ نسبت تصویر و تراکم متن باید مختص feature تعریف شود |
| C-05 | فیلد فرم | `.tp-field`، `.tp-hint`، `.tp-error-text` | ورودی متن، انتخاب و توضیح | عادی، focus، invalid، disabled، readonly؛ خطا کنار همان فیلد |
| C-06 | جست‌وجو | `.sbar` و `input[type=search]` | جست‌وجوی فهرست | خالی، دارای عبارت، بدون نتیجه، خطا؛ پاک‌سازی فارسی با تابع مشترک `nz` |
| C-07 | تب | `tpTabs()` و `[role=tab]` | بخش‌های هم‌سطح و قابل تعویض | selected، focus؛ کلیدهای جهت‌دار و ارتباط tabpanel لازم است |
| C-08 | Breadcrumb | `crumb()` | سلسله‌مراتب صفحه | آخرین بخش با `aria-current=page` |

| C-10 | منوی کشویی | `details.tp-dropdown` | منوی حساب/اقدام | باز/بسته، Escape و focus باید بازبینی شود |

| C-12 | Toast | `toast(text, type)` | بازخورد کوتاه عملیات | موفق/خطا/اطلاع؛ برای خطاهای فرم جایگزین پیام فیلدی نیست |
| C-13 | وضعیت صفحه | `tpState('empty'|'error'|'loading', ...)` | خالی، خطا، بارگذاری | عنوان و توضیح عملی؛ CTA فقط وقتی مسیر واقعی وجود دارد |
| C-14 | اسکلت و Spinner | `.tp-skeleton`، `.tp-spinner` | انتظار داده | ابعاد باید از چیدمان نهایی پیروی کند؛ shimmer با reduced-motion حذف شود |
| C-15 | جایگاه رسانه | `.ph` | تصویر/ویدئو و placeholder حصیری | حالت واقعی تصویر و جایگاه خالی باید قابل تمایز باشند |
| C-16 | 404 | `nfp()` | مسیر نامعتبر | بازگشت امن به خانه یا فهرست مربوط |

## ۴. قرارداد حالت‌ها

هر جزء تعاملی باید فقط حالت‌های مرتبط را داشته باشد؛ اضافه‌کردن نمایشی همهٔ حالت‌ها لازم نیست.

- **Default:** بدون انتخاب یا خطا.
- **Hover:** فقط برای دستگاه دارای pointer؛ عملکرد نباید به hover وابسته باشد.
- **Focus-visible:** حلقهٔ طلایی روشن با offset؛ ترتیب Tab قابل پیش‌بینی.
- **Pressed/Active:** بازخورد کوتاه، بدون تغییر ابعاد والد و بدون layout shift.
- **Selected:** ویژگی معنایی ARIA و وضعیت ظاهری هم‌زمان.
- **Disabled:** قابل تشخیص، غیرقابل اجرا، با توضیح علت در موارد مهم.
- **Loading:** کنترل تکرار کلیک؛ spinner همراه متن قابل فهم.
- **Invalid:** خطای متصل به فیلد و حفظ مقدارهای سالم.
- **Success:** تنها بعد از پاسخ معتبر عملیات، نه پس از کلیک.
- **Empty/Error:** توضیح علت محتمل و اقدام قابل انجام؛ از پیام «چیزی نیست» بدون مسیر بعدی پرهیز شود.

## ۵. قواعد استفاده و توسعه

1. ابتدا از جزء موجود استفاده شود؛ جزء جدید فقط وقتی اضافه شود که الگوی فعلی پاسخ‌گوی نیاز نیست.
2. استایل feature-specific در CSS صفحه یا feature بماند و به `.card` یا `.btn` عمومی تحمیل نشود.
3. نام کلاس و رفتار جزء در همین کاتالوگ ثبت شود؛ CSS منبع تغییر کند، نه `dist` یا `django/static/css/tatami.css`.
4. HTML تولیدی باید label، role، name، state، alt و focus مناسب داشته باشد.
5. برای فرم‌های Django، خطاهای field و non-field و مقادیر برگشتی حفظ شوند؛ پیام toast به‌تنهایی کافی نیست.
6. آزمون جزء در سه سطح انجام شود: رفتار، نمایش RTL در موبایل، و دسترسی با کیبورد/Screen Reader.

## ۶. دروازهٔ پذیرش

یک جزء وقتی استاندارد محسوب می‌شود که API/markup، کلاس، وضعیت‌های مجاز، نمونهٔ استفاده، breakpointها، رفتار keyboard، متن/رنگ کنتراست و تست رگرسیون آن ثبت شده باشد.
