## ۱. هدف پروژه

بازطراحی کامل تجربهٔ تاتامی پلاس با حفظ قابلیت‌ها، مسیرها، قراردادهای داده و رفتارهای سالم فعلی؛ با هویت بصری تاریک، سینمایی و ممتاز بر پایهٔ زغالی، قرمز تاتامی و طلایی. هر صفحه باید متناسب با وظیفه و گردش‌کار خودش طراحی شود. استفاده از یک قالب تکراری برای همهٔ صفحات قابل قبول نیست.

طراحی صفحات حتی در بخش‌هایی که بک‌اند ندارند انجام می‌شود؛ اما اتصال عملیاتی، نمایش دادهٔ واقعی و ادعای عملکرد فقط در محدوده‌ای مجاز است که قرارداد Django آن را واقعاً پشتیبانی می‌کند.

## ۳. قواعد غیرقابل مذاکره

1. **دادهٔ جعلی ممنوع:** عدد فروش، قیمت، موجودی، امتیاز، تعداد هنرجو، فاصله، تراکنش یا پروفایل ساختگی نباید به‌عنوان دادهٔ واقعی نمایش داده شود.
2. **طراحی بدون بک‌اند مجاز است:** صفحات فاقد API یا View واقعی با حالت‌های خالی، توضیح محدودیت، اسکلت بارگذاری و CTA غیرفعالِ توضیح‌دار طراحی می‌شوند؛ نه با سرویس یا نتیجهٔ ساختگی.
3. **مرجع عملیات، Django است:** Session، CSRF، مجوز، اعتبارسنجی، قیمت نهایی، موجودی، پرداخت و وضعیت سفارش فقط از سرور معتبرند.
4. **بدون تغییر بک‌اند:** مدل، migration، Python، URL، View، Form، تنظیمات هاست، WSGI، Passenger، دیتابیس و انتشار زنده خارج از محدودهٔ این کار هستند.
5. **بدون مهاجرت سراسری React:** معماری فعلی حفظ می‌شود. اگر جزیرهٔ تعاملی مستقلی واقعاً لازم شد، جداگانه توجیه و محدود می‌شود.
6. **مالک DOM یکتا:** Router، Django bridge و هر UI جدید نباید هم‌زمان یک root را render کنند.
7. **منبع را تغییر بده، نه خروجی را:** تغییر CSS/JS باید در منبع درست اعمال و از Build عبور داده شود.
8. **هر بسته کوچک و قابل بازگشت:** هدف، فایل‌های تغییرکرده، تست، نتیجه و روش rollback باید روشن باشند.

## ۵. معیار پایان هر صفحه

یک صفحه فقط وقتی «تمام‌شده» محسوب می‌شود که:
- هدف و نقش مجاز آن روشن باشد؛
- route مستقیم و ناوبری داخلی درست کار کند؛
- منبع تمام داده‌ها مشخص باشد؛
- حالت‌های loading، empty، error، success و forbidden متناسب با نیاز طراحی شده باشند؛
- هیچ دادهٔ نمونه به‌جای دادهٔ واقعی جا نزده باشد؛
- در موبایل، دسکتاپ، RTL و کیبورد قابل استفاده باشد؛
- با صفحه‌های مجاور و قرارداد Django تعارض نداشته باشد؛
- تست رگرسیون مربوط اجرا شده و نتیجه ثبت شده باشد.

## ۶. ریسک‌های شناخته‌شدهٔ ابتدای کار

- سند معماری قدیمی به SHA قبلی بک‌اند اشاره می‌کرد؛ این مبنا در همین بسته به SHA فعلی اصلاح می‌شود.

- پنل مارکتینگ به JSON API فرضی تکیه دارد؛ قرارداد فعلی Django برای CMS، Django Admin و رندر سمت سرور است.
- داده‌های داشبورد/فروشگاه/مربی/دوره در بخشی از Preview نمونه‌اند و نباید دادهٔ واقعی قلمداد شوند.
- دروازهٔ پرداخت فعلی آزمایشی است؛ نمایش موفقیت مالی فقط با تأیید سرور مجاز است.
