# طرح انتقال کاتالوگ فروشگاه تاتامی پلاس

وضعیت: آماده‌سازی فرانت‌اند و قرارداد داده؛ هنوز هیچ داده‌ای در دیتابیس سرور وارد نشده است.  
دامنه: کاتالوگ ۵۹ محصول منبع فرانت‌اند، نمایش وضعیت واقعی موجودی و الگوی مشترک کارت محصول.  
مرز مسئولیت: در این مرحله هیچ مدل، View، URL، Form، migration، تنظیمات یا داده زنده بک‌اند تغییر نمی‌کند.

## 1. منبع و ممیزی داده

منبع مرجع: \`shared/src/data/store-products.json\`  
تعداد رکورد: ۵۹  
دسته‌ها: ۷  
منابع قیمت: ترب و دیجی‌کالا  
تاریخ ثبت قیمت مرجع: ۱۴۰۵/۰۷/۲۸  
تصاویر محلی متناظر در repo: ۵۹ مورد در \`preview/assets/images/products/\`

این داده‌ها، کاتالوگ مرجع بازار هستند؛ نه لیست کالاهای تأییدشده و آماده فروش تاتامی پلاس. قیمت‌ها از منابع بیرونی‌اند و نباید وارد \`ProductVariant.price\` شوند. برچسب فروشگاهِ منبع نیز گاهی نام فروشنده نیست و عباراتی مانند «چند فروشگاه» دارد.

سه نمونه آزمایشی اضافه‌شده در runtime فرانت‌اند، از این بسته حذف شده‌اند. فقط ۵۹ رکورد واقعی موجود در فایل منبع انتخاب شده‌اند.

## 3. سه وضعیت موجودی که باید از هم تفکیک شوند

صرفاً دو وضعیت «موجود/ناموجود» کافی نیست، چون نبود اطلاعات با موجودی صفر یکسان نیست:

- \`in_stock\`: دست‌کم یک تنوع فعال با موجودی ثبت‌شده بیشتر از صفر.
- \`out_of_stock\`: تنوع‌های فروش معتبر ثبت شده‌اند، اما مجموع موجودی قابل فروش صفر است.
- \`inventory_unregistered\`: هنوز تنوع فروش، قیمت فروش یا موجودی واقعی برای محصول ثبت نشده است.

هیچ محصولی فقط به‌دلیل نبود variant نباید «ناموجود فیزیکی» اعلام شود. این حالت باید «موجودی ثبت نشده» باشد.

## 4. مانع فعلی در View فروشگاه

در \`store.views.product_list\` فعلی:
- فقط Product فعال و Category فعال انتخاب می‌شود.
- \`starting_price\` از variant فعال با \`stock_quantity > 0\` محاسبه می‌شود.
- سپس \`starting_price__isnull=False\` اعمال می‌شود.

بنابراین محصول بدون variant یا با موجودی صفر اصلاً در لیست ظاهر نمی‌شود. قالب به‌تنهایی نمی‌تواند آن را نمایش دهد. برای نمایش کارت‌های موجود/ناموجود/ثبت‌نشده، تیم بک‌اند باید query و context را توسعه دهد.

قرارداد پیشنهادی context برای هر محصول:
- \`availability_status\`: یکی از سه مقدار بالا.
- \`available_stock\`: مجموع موجودی قابل فروش؛ فقط از variantهای فعال.
- \`starting_price\`: کمترین قیمت فروش ثبت‌شده برای variant فعال؛ هرگز قیمت مرجع بازار.
- \`has_sellable_variant\`: آیا حداقل یک تنوع با قیمت معتبر و فعال وجود دارد.
- \`images\`: تصاویر تأییدشده ProductImage.

فیلترهای قیمت و سایز باید روی variantهای فعال اعمال شوند. variant ناموجود نباید امکان افزودن به سبد داشته باشد. کنترل نهایی موجودی و قیمت همچنان در POST سمت سرور انجام شود.

## 5. الگوی شیءگرا/کامپوننت‌محور کارت محصول

در لایه فرانت‌اند، کارت باید یک Template Component مستقل باشد:
\`django/templates/components/store_product_card.html\`

قرارداد ورودی پیشنهادی:
- \`product\`: شیء Product از Django.
- \`availability_status\`: وضعیت واقعی از context سرور.
- \`available_stock\`: موجودی واقعی.
- \`starting_price\`: کمترین قیمت فروش واقعی یا None.
- \`image\`: تصویر اول تأییدشده یا None.

این کامپوننت مالک markup کارت است. صفحه فهرست فقط داده را پاس می‌دهد؛ صفحه جزئیات و پیشنهادهای محصول هم باید در صورت استفاده از کارت، همان کامپوننت را reuse کنند. CSS کارت نیز باید تحت یک ریشه مانند \`.tp-store-page .tp-product-card\` بماند.

ظاهر مرجع:
- کلاس‌های فعلی \`card pcd tp-product-card\`
- تصویر با نسبت ۴:۳
- grid مبتنی بر حداقل عرض کارت
- ارتفاع همسان کارت‌ها و چسبیدن قیمت/CTA به پایین کارت
- دو ستون در موبایل باریک، مطابق CSS فعلی پروژه
- نشان وضعیت فقط بر اساس \`availability_status\` سرور

این کامپوننت نباید موجودی، قیمت، وضعیت فروش یا مجازبودن خرید را در JavaScript محاسبه کند.

## 6. الزامات قبل از Import واقعی

1. مسئول فروش باید قیمت فروش تاتامی پلاس را برای هر محصول/variant تأیید کند.
2. برای هر variant، سایز و رنگ دقیق از منبع فروش/کالا ثبت شود.
3. موجودی فیزیکی شمارش و در سرور ثبت شود؛ «عدد نامشخص» به صفر یا عدد نمونه تبدیل نشود.
4. مجوز استفاده از ۵۹ تصویر بررسی شود. وجود تصویر در repo به معنی مجوز انتشار نیست.
5. مسیر Media در هاست production تأیید شود. تنظیمات فعلی \`MEDIA_ROOT\`/\`MEDIA_URL\` به‌تنهایی تضمین نمی‌کند cPanel در production تصاویر را serve کند.
6. Import باید idempotent باشد: اجرای دوباره نباید دسته، محصول، variant یا تصویر تکراری بسازد.
7. قبل از import، از دیتابیس backup گرفته شود و dry-run گزارش تفاوت‌ها تولید کند.

## 7. ترتیب اجرای امن

1. تأیید schema و قرارداد context توسط مسئول بک‌اند.
2. dry-run برای تطبیق دسته‌ها و محصولات موجود و تولید گزارش duplicate/conflict.
3. import فقط Category و Product به‌عنوان catalog item غیرقابل خرید، بدون قیمت/موجودی فرضی.
4. افزودن تصاویر فقط بعد از تأیید حقوق و Media storage.
5. ثبت قیمت فروش، variant و موجودی واقعی توسط داده معتبر فروشگاه.
6. تغییر View برای نمایش هر سه وضعیت و خروجی context استاندارد.
7. پیاده‌سازی و استفاده از Template Component مشترک در فهرست، جزئیات و پیشنهادها.
8. تست فیلتر، مرتب‌سازی، صفحه‌بندی، detail، سبد، out-of-stock و جلوگیری از افزودن variant ناموجود.

## 8. معیارهای پذیرش

- ۵۹ رکورد منبع با کلیدهای یکتا و بدون حذف ناخواسته.
- ۷ دسته‌بندی با تطبیق دقیق نام‌ها.
- هیچ reference_price در ProductVariant.price قرار نگیرد.
- هیچ stock quantity از فرانت‌اند یا مقدار پیش‌فرض نمایشی کپی نشود.
- همه محصولات دارای یکی از سه وضعیت معتبر باشند.
- فقط \`in_stock\` امکان افزودن به سبد داشته باشد.
- قیمت/موجودی در سمت سرور دوباره اعتبارسنجی شود.
- تصویر فقط از Media مورد تأیید یا تصویر fallback مجاز بارگذاری شود.
- کارت‌ها در همه صفحات از یک Template Component مشترک و CSS مشترک استفاده کنند.

## 9. وضعیت فعلی

این سند و فایل JSON فقط بسته آماده‌سازی برای انتقال هستند. دیتابیس production تغییر نکرده، هیچ محصولی هنوز در سرور ایجاد نشده و هیچ محصولی برای خرید فعال نشده است. انجام import زنده مستلزم اجرای مسئول بک‌اند روی دیتابیس واقعی و تکمیل اطلاعات واقعی فروش/موجودی است.
