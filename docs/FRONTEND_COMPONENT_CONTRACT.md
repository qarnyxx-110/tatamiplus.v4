# قرارداد معماری رابط کاربری تاتامی پلاس

نسخه: 1.0  
دامنه: لایه فرانت‌اند Django Templates، CSS و JavaScript  
اصل معماری: Design Tokens + Template Inheritance + Component Composition

## 1. هدف

تمام صفحات باید از یک زبان طراحی، قرارداد ساختاری و قواعد واکنش‌گرایی مشترک استفاده کنند. اصلاح یک کامپوننت یا Layout استاندارد باید بدون بازنویسی دستی همه صفحات، روی تمام مصرف‌کنندگان همان جزء اثر بگذارد.

این قرارداد به معنی تبدیل Django Templates به یک فریم‌ورک شیءگرا نیست. الگوی مناسب این پروژه، ترکیب وراثت قالب (Template Inheritance)، ترکیب اجزا (Include/Composition)، کلاس‌های کوچک JavaScript و CSS مبتنی بر توکن‌ها است.

## 2. لایه‌های معماری

1. **Design Tokens:** رنگ، تایپوگرافی، فاصله، شعاع، سایه، لایه‌بندی، حرکت و breakpointها. منبع مرجع: \`shared/src/design/tokens.json\`.
2. **Foundation:** reset، تایپوگرافی پایه، RTL، کنترل‌های فرم و قواعد دسترس‌پذیری. منبع: \`shared/src/css/base.css\`.
3. **UI Components:** دکمه، فیلد، کارت، پیام، وضعیت خالی، نشان، صفحه‌بندی و اجزای تکرارشونده. منابع: \`shared/src/css/components.css\`، \`shared/src/css/ui.css\` و \`django/templates/components/\`.
4. **Layouts:** ترکیب‌های پایدار صفحه مانند \`layouts/auth.html\`، فرم، محتوای استاندارد و پنل. Layout مالک عرض، ستون‌بندی، فاصله و جایگاه اجزای مشترک است.
5. **Page Templates:** صفحات دامنه‌ای مانند حساب، فروشگاه، دوره، مربی و سفارش. صفحه فقط محتوای خاص خودش و اتصال به context را مشخص می‌کند.
6. **Behavior:** رفتارهای تعاملی کوچک و مستقل در JavaScript. منطق تجاری، مجوز، محاسبه و اعتبارسنجی authoritative متعلق به بک‌اند باقی می‌ماند.

## 3. قرارداد نام‌گذاری

- کلاس‌های متعلق به سیستم طراحی با پیشوند \`tp-\` نام‌گذاری می‌شوند.
- نام پایه بیانگر جزء است: \`tp-card\`، \`tp-field\`، \`tp-alert\`.
- تغییر ظاهری با modifier مشخص می‌شود: \`tp-button--primary\` یا \`tp-card--compact\`.
- وضعیت تعاملی با \`is-\` یا ویژگی ARIA بیان می‌شود: \`is-loading\`، \`aria-expanded\`، \`aria-invalid\`.
- selectorهای عمومی مانند \`nav\`، \`section\` یا \`input\` فقط برای reset و رفتارهای واقعاً سراسری مجازند؛ ظاهر یک ناحیه باید به ریشه همان ناحیه محدود شود.
- کلاس‌های صفحه‌ای باید به ریشه صفحه scope شوند؛ برای نمونه \`.tp-store-page ...\`.

## 4. قرارداد Layout

هر Layout باید:
- یک ریشه مشخص و قابل شناسایی داشته باشد؛ مانند \`data-page-layout="auth"\`.
- عرض و max-width را خودش تعریف کند؛ صفحه مصرف‌کننده نباید با کلاس محدودکننده دیگری آن را ناخواسته کوچک کند.
- برای فرزندان Grid/Flex مقدار \`min-width: 0\` را رعایت کند تا متن یا input باعث overflow نشود.
- ترتیب و رفتار موبایل/دسکتاپ را یک‌بار تعریف کند.
- فقط نقطه‌های توسعه کنترل‌شده با block ارائه کند.
- منطق یا داده تجاری در آن قرار نگیرد.

صفحات نباید هم‌زمان چند utility متناقض برای عرض داشته باشند. مثال ممنوع در Layout دو‌ستونه: ترکیب یک کلاس محدودکننده تک‌ستونه مثل \`tp-auth\` با \`tp-auth-layout\`.

## 5. قرارداد کامپوننت

هر کامپوننت باید یک مسئولیت مشخص داشته باشد:
- ساختار HTML و کلاس‌های استاندارد را ارائه کند.
- داده را از context یا پارامترهای include دریافت کند.
- مسیر یا عملیات بک‌اند را خودسرانه تولید نکند.
- قوانین قیمت، موجودی، نقش یا مجوز را محاسبه نکند.
- حالت‌های پیش‌فرض، خطا، خالی و غیرفعال را در صورت نیاز پوشش دهد.
- از توکن‌ها و کنترل‌های مشترک استفاده کند.

کامپوننت موجود \`includes/form_fields.html\` حفظ و به‌عنوان جزء مشترک فرم استفاده می‌شود؛ از ساخت نسخه موازی با همان مسئولیت پرهیز شود.

## 6. قرارداد فرم و احراز هویت

فرم‌ها باید:
- از فیلدهای واقعی Django و نام دقیق آن‌ها استفاده کنند.
- برای تمام POSTها \`{% csrf_token %}\` داشته باشند.
- خطای کلی و خطای هر فیلد را نزدیک محل مربوط نشان دهند.
- label واقعی و شناسه یکتا داشته باشند.
- پیام راهنما و خطا را به فیلد مرتبط کنند.
- پس از submit وضعیت بارگذاری و غیرفعال شدن کنترل‌ها را قابل فهم نمایش دهند.
- هیچ رمز، OTP، Session یا داده حساس را در LocalStorage نگه ندارند.

قرارداد بک‌اند موجود که در این نمونه بدون تغییر حفظ شده است:
- ورود: \`phone\`، \`role\` و hidden field با نام \`next_url\`؛ فرم \`PhoneLoginForm\`.
- تأیید OTP: فیلد \`code\`؛ فرم \`OTPVerifyForm\`.
- تکمیل پروفایل: \`name\`، \`city\` و \`role\`؛ فرم \`ProfileCompletionForm\`.
- مسیرهای موجود: \`phone_auth:login\`، \`phone_auth:verify_otp\` و \`phone_auth:send_otp\`.

قالب‌ها نباید ترتیب مراحل، اعتبار OTP، محدودیت ارسال یا نقش مجاز را مستقل از بک‌اند پیاده کنند.

## 7. قرارداد واکنش‌گرایی

- مبنای طراحی mobile-first است؛ عرض 360 پیکسل باید پشتیبانی شود.
- در اندازه‌های کوچک، ستون‌های غیرضروری به یک ستون تبدیل می‌شوند.
- Gridها از \`minmax(0, 1fr)\` استفاده می‌کنند؛ عرض ثابت برای ستون محتوایی ممنوع است مگر جزء ذاتاً اندازه ثابت داشته باشد.
- input، select، textarea و دکمه‌ها نباید از والد بیرون بزنند.
- متن فارسی باید بدون بریدگی یا ستون‌های باریک غیرطبیعی نمایش داده شود.
- جدول‌های عریض باید راهکار overflow کنترل‌شده داشته باشند.
- مقادیر breakpoint باید از سیستم توکن یا قرارداد مرکزی گرفته شوند، نه اینکه هر صفحه breakpoint سلیقه‌ای جدید بسازد.

## 8. قرارداد CSS و تولید خروجی

- منبع اصلی CSS مشترک، فایل‌های \`shared/src/css/\` است.
- \`django/static/css/tatami.css\` خروجی تولیدشده با \`node shared/build.js\` است؛ ویرایش دستی آن ممنوع است.
- CSS ماژولار فقط برای قواعد اختصاصی یک حوزه نگهداری می‌شود و باید به ریشه همان صفحه scope شود.
- CSS قدیمی یا تکراری پس از بررسی مصرف‌کنندگان حذف می‌شود، نه به‌صورت حدسی.
- ترتیب بارگذاری stylesheetها باید ثابت و مشخص باشد.

## 9. قرارداد JavaScript

- هر controller یک مسئولیت محدود دارد و باید قابل نصب مجدد بدون ثبت event listener تکراری باشد.
- رفتارهای وابسته به DOM باید پس از render صفحه نصب شوند و در صورت جایگزینی DOM، دوباره به شکل idempotent اجرا شوند.
- کد UI فقط نمایش و تعامل را مدیریت می‌کند؛ داده authoritative از سرور می‌آید.
- خطای شبکه، پاسخ نامعتبر و حالت بارگذاری باید قابل مشاهده باشند.
- رفتارهای حساس مثل احراز هویت، مجوز، قیمت، موجودی و ثبت سفارش در مرورگر پیاده‌سازی نمی‌شوند.

## 10. نمونه مرجع احراز هویت

\`layouts/auth.html\` پوسته مشترک صفحه احراز هویت را تعریف می‌کند. این Layout عرض، Grid دو‌ستونه دسکتاپ، ترتیب موبایل و کارت معرفی را کنترل می‌کند.

\`components/auth_aside.html\` کارت معرفی مشترک را ارائه می‌دهد.

سه صفحه زیر فقط محتوای اختصاصی فرم را تعریف می‌کنند:
- \`accounts/login.html\`
- \`accounts/otp_verify.html\`
- \`accounts/complete_profile.html\`

همه آن‌ها از \`includes/form_fields.html\` استفاده می‌کنند. نام فیلدها، action، CSRF، فرم‌ها و رفتار سمت سرور تغییر نمی‌کنند.

## 11. معیار پذیرش هر Layout و Component

- قالب Django بدون خطا compile شود.
- هیچ فرزند Grid/Flex باعث overflow نشود.
- در اندازه‌های 360، 390، 600، 768، 900، 1024 و 1440 پیکسل چیدمان قابل استفاده بماند.
- حالت focus، خطا، disabled و loading قابل مشاهده باشد.
- هیچ route، نام فیلد، CSRF یا قرارداد context بدون نیاز تغییر نکند.
- تغییر یک کامپوننت فقط روی مصرف‌کنندگان مورد انتظار اثر بگذارد.
- خروجی CSS با build script قابل بازتولید باشد.

## 12. دامنه این مرحله

این مرحله فقط قرارداد معماری و نمونه احراز هویت را پیاده می‌کند. بازآرایی سایر صفحات، فروشگاه، هدر مشترک Preview/Django و بازآرایی کامل JavaScript در مراحل مستقل و پس از تأیید انجام خواهند شد.

هیچ فایل مدل، View، URL، Form، تنظیمات، پایگاه داده یا منطق بک‌اند در این مرحله تغییر نمی‌کند.
