# معماری فعال فرانت‌اند تاتامی پلاس

**وضعیت:** مرجع فعال برای تغییرات فرانت‌اند  
**تاریخ بازبینی:** ۲۱ نوامبر ۲۰۲۶  
**مبنای کد فرانت‌اند:** شاخهٔ `feat/frontend-section-consolidation-20261121`، commit `254d1bdc05e801ccc337f9c8c61bd26c565a85bc`  
**مبنای قرارداد Django:** شاخهٔ `main` مخزن `Radinsharifi/Tatami-demo`، commit `20e96721cc1a589d625fecd3fffa9ec42b1fc64f`

این سند دربارهٔ معماری موجود و مسیر تغییر آن است؛ به‌تنهایی مجوز تغییر بک‌اند یا انتشار روی سایت زنده نیست.

## ۱. اصولی که نباید شکسته شوند

1. **مالکیت فرانت‌اند:** این مخزن مسئول HTML، CSS، JavaScript، واکنش‌گرایی، دسترس‌پذیری، تست مرورگر و بستهٔ تحویل فرانت‌اند است. منطق Python، مدل‌ها، migration، URL، View، Form، مجوز، Session، موجودی، قیمت نهایی و قواعد تجاری متعلق به مخزن Django هستند.
2. **منبع حقیقت داده:** هرجا Django مسیر و صفحهٔ واقعی دارد، داده و نتیجهٔ عملیات باید از همان بک‌اند بیاید. دادهٔ محلی فقط با برچسب روشن «نمونه/پیش‌نمایش» مجاز است و نباید جای دادهٔ واقعی، موجودی، قیمت، سفارش یا هویت کاربر بنشیند.
3. **حفظ Preview:** `https://tatamiplus.ir/preview/` مسیر عمومی استاتیک است. تغییرات فرانت‌اند نباید مسیر Passenger، `.htaccess`، WSGI یا ریشهٔ سرویس Django را دست‌کاری کند.
4. **تغییر کوچک و قابل بازگشت:** هر تغییر باید یک هدف مشخص، فایل‌های محدود، تست مرتبط، مانیفست روشن و راه بازگشت داشته باشد.
5. **بدون بازنویسی یک‌باره:** هیچ مهاجرت سراسری به React، تعویض Router یا بازنویسی کامل CSS صرفاً به‌خاطر سلیقه انجام نمی‌شود.

## ۲. تصویر واقعی معماری فعلی

### ساخت و خروجی‌ها

- نقطهٔ Build: `shared/build.js`.
- فرمان ساخت: از پوشهٔ `shared/` دستور `npm run build` یا `node build.js`.
- خروجی‌ها: `shared/dist/student/`، `coach/`، `club/`، `marketing/` و `preview/`.
- سه PWA نقش‌محور از یک پوسته و کد مشترک استفاده می‌کنند؛ تنظیم نقش و فهرست ناوبری هرکدام در تنظیمات Build تعریف می‌شود.
- Preview یک خروجی مستقل است که کد `django-route-bridge.js` را نیز در انتهای اسکریپت خود دریافت می‌کند.
- Build فعلی عمدتاً فایل‌های JavaScript را به‌ترتیب مشخص‌شده به هم متصل می‌کند؛ این پروژه فعلاً یک برنامهٔ مبتنی بر ES Moduleهای مستقل با import/export نیست. ترتیب فایل‌ها و نام‌های سراسری اهمیت دارند.

### فایل منبع در برابر خروجی تولیدشده

فایل‌های داخل `shared/src/` و ورودی‌های `shared/build.js` منبع تغییر هستند. این فایل‌ها را دستی ویرایش نکنید، چون Build آن‌ها را بازتولید می‌کند:

- `shared/dist/**`
- `shared/build-artifact.html`
- `django/static/css/tatami.css`

برای اصلاح CSS یا JS خروجی، فایل منبع را تغییر دهید و Build را دوباره اجرا کنید.

## ۳. مرز مالکیت در مرورگر

- در اجرای معمول Preview/PWA، `router.js` مالک ناوبری hash و رندر محتوای `#app` است.
- در دامنهٔ زنده و مسیر `/preview/`، `router.js` برای فهرست مشخصی از hashها کنترل را به پل Django واگذار می‌کند.
- `django-route-bridge.js` HTML واقعی هم‌مبدأ Django را دریافت می‌کند و آن را در پوستهٔ Preview نمایش می‌دهد. Session و CSRF همچنان متعلق به Django هستند.
- در هر لحظه فقط یک لایه باید مالک رندر یک ناحیهٔ DOM باشد. Router قدیمی، پل Django و React نباید هم‌زمان یک عنصر مثل `#app` را کنترل کنند.
- اگر در آینده React لازم شد، فقط در یک ریشهٔ کوچک و مشخص مانند `[data-tp-island]` mount شود؛ مالکیت آن ریشه، lifecycle و unmount باید مستقل و تست‌شده باشد.

## ۴. داده و اتصال واقعی به Django

مرجع جزئیات URLها، فیلد فرم‌ها، CSRF و selectorهای قالب، سند `django/STORE_CHECKOUT_FRONTEND_HANDOFF.md` است. خلاصهٔ وضعیت:

| بخش | قرارداد واقعی موجود | وضعیت پل Preview در این نسخه |
|---|---|---|
| ورود با رمز | `/auth/login/` | متصل |
| ورود/ثبت‌نام پیامکی | `/auth/login/sms/`، سپس OTP و تکمیل پروفایل | متصل |
| بازیابی/تنظیم رمز | `/auth/password/reset/` و `/auth/password/set/` | مسیرهای شروع و تنظیم متصل |
| فروشگاه و سبد | `/store/`، جزئیات محصول، `/store/cart/` و POSTهای واقعی | متصل؛ قیمت و موجودی مرجع فقط Django است |
| Checkout و پرداخت | `/checkout/address/`، `/checkout/review/`، `/checkout/pay/` و callback | متصل؛ عملیات مالی فقط سمت سرور |
| دوره‌ها | `/club/` و `/club/course/<slug>/` | متصل؛ دادهٔ دورهٔ نمونه در Preview نباید محتوای منتشرشده تلقی شود |
| مربیان | `/coaches/`، پروفایل و درخواست مربیگری | متصل |
| جم | `/account/gems/` | متصل |
| وبلاگ | `/blog/` و `/blog/<str:slug>/`؛ فقط مطالب منتشرشده | **هنوز به hashهای Preview وصل نشده**؛ فعلاً یک مورد باز برای ممیزی/اتصال |
| تاتامی‌پدیا | route یا مدل متناظر در Django فعلی ندارد | UI و دادهٔ محلی؛ برچسب نمونه و جداسازی حفظ شود |
| نقشهٔ باشگاه‌ها | قرارداد جست‌وجوی جغرافیایی/موقعیت در Django فعلی ندارد | نمونه/فرانت‌اندی؛ فاصله و مختصات ساختگی نباید واقعی نمایش داده شوند |
| مربی آنلاین و AI | endpoint یا مدل عملیاتی متناظر تأیید نشده | رابط فرانت‌اندی؛ نباید ادعای تحلیل یا اتصال واقعی کند |
| داشبوردهای نقش‌محور | بعضی داده‌ها هنوز قرارداد عملیاتی ندارند | فقط بخش‌های دارای منبع واقعی متصل؛ باقی موارد نمایشی و برچسب‌دار |

**نکته دربارهٔ JSON API:** `docs/API_CONTRACT.md` یک پیشنهاد تاریخی برای API است، نه API فعلی Django. `tools/mock-api-server.mjs` فقط برای تست است. `TP_API_BASE` و fallback محلی در `shared/src/js/shared/api.js` را به‌عنوان اتصال production به بک‌اند Django در نظر نگیرید. منبع فعلی صفحات عملیاتی، route و قالب Django است؛ نه mock API و نه دادهٔ محلی.

## ۵. روش ممیزی هر صفحه پیش از تغییر

برای هر صفحه/بخش، قبل از ویرایش، این موارد ثبت و بررسی می‌شوند:

1. مسیرهای hash و URLهای مستقیم؛ مسیر قدیمی و مقصد نهایی.
2. فایل View و CSS مالک آن؛ فایل‌های مشترکی که روی صفحه اثر می‌گذارند.
3. منبع هر مقدار: Django، JSON واقعی، دادهٔ ثابت، localStorage یا دادهٔ نمونه.
4. فرم‌ها، فیلدها، روش GET/POST، CSRF، Session و مجوز سمت سرور.
5. حالت‌های loading، خالی، خطا، دسترسی غیرمجاز و نتیجهٔ نامعتبر.
6. رفتار موبایل، RTL، keyboard/focus، reduced-motion و دسترس‌پذیری.
7. آزمون‌های لازم برای مسیر موفق و سناریوهای شکست.
8. محدودهٔ فایل‌هایی که اصلاح می‌شوند و فایل‌هایی که عمداً تغییر نمی‌کنند.

تا وقتی منبع داده و قرارداد یک صفحه روشن نشده، نباید با دادهٔ نمونه یا API فرضی آن را «متصل» نشان داد.

## ۶. قواعد تغییر و ماژولار کردن

### تغییر کوتاه‌مدت

- ابتدا تست‌های موجود و خروجی Build اجرا می‌شوند؛ سپس تغییر انجام می‌شود.
- هر اصلاح به یک هدف مشخص محدود می‌شود. تغییر هم‌زمان Router، مدل داده، طرح CSS و مسیر Django بدون نیاز اثبات‌شده ممنوع است.
- نام و رفتار مسیرهای قدیمی حفظ می‌شوند، مگر مقصد جدید مستند و با تست پوشش داده شود.
- state مرورگر ورودی غیرقابل‌اعتماد است؛ اعتبارسنجی `state-guard.js` دور زده نمی‌شود.
- قیمت، موجودی، مجوز، پرداخت، وضعیت سفارش و مالکیت حساب هرگز از localStorage یا محاسبهٔ مرورگر معتبر نمی‌شوند.

### مرحلهٔ اول ماژولار کردن: پل Django

`django-route-bridge.js` اکنون حدود ۷۹۰ خط دارد و چند مسئولیت را در یک فایل جمع کرده است: تبدیل مسیرها، resolve کردن شناسه‌های محصول/مربی/دوره، fetch و رندر سند، ارتقای فرم/لینک، ناوبری و مدیریت POST. این گلوگاه بعدی ماژولار کردن است.

تقسیم پیشنهادی، بدون تغییر رفتار:

- route map و policy مقصدهای مجاز؛
- resolverهای محصول، دوره و مربی؛
- دریافت صفحه و کنترل درخواست‌های لغوشدنی؛
- رندر و پاک‌سازی/ارتقای HTML؛
- مدیریت فرم‌ها و POST/CSRF؛
- ناوبری، history و پیام‌های خطا.

در مرحلهٔ اول، فایل ورودی فعلی حفظ می‌شود و به‌صورت facade فقط اجزای جداشده را هماهنگ می‌کند. به دلیل Build مبتنی بر الحاق، هر فایل جدید باید در ترتیب Build ثبت و در scope امن (IIFE یا namespace مشخص) قرار گیرد؛ اضافه‌کردن `const`های سراسری تکراری می‌تواند کل برنامه را از کار بیندازد.

### مرحلهٔ دوم: مالکیت featureها

هر feature باید یک ورودی/مسئولیت روشن برای render، state و eventهای خودش داشته باشد. state موقت یک صفحه نباید بدون نیاز به global تبدیل شود. نام‌های عمومی قدیمی فقط از طریق facade سازگاری نگه داشته می‌شوند تا انتقال تدریجی ممکن باشد.

### React و OOP

- در وضعیت فعلی، مهاجرت کامل به React توجیه فنی اثبات‌شده ندارد و خطر دو مالک برای DOM و شکستن پل Django را بالا می‌برد.
- اگر یک قابلیت پیچیده واقعاً به state و interaction زیاد نیاز داشت، ابتدا یک React island مستقل با ریشه و lifecycle مشخص بررسی می‌شود.
- معماری feature-based و توابع/ماژول‌های کوچک اولویت دارند. کلاس فقط وقتی استفاده می‌شود که شیء واقعاً lifecycle و state مستقل دارد؛ ایجاد کلاس برای هر View یا helper هدف معماری نیست.

## ۷. ترتیب ادامهٔ ممیزی

1. تثبیت قرارداد احراز هویت و CI روی revision فعلی بک‌اند.
2. فروشگاه، جزئیات محصول، سبد، نشانی، بازبینی و پرداخت؛ با تأکید بر server-authoritative بودن قیمت/موجودی.
3. باشگاه مجازی و مربیان؛ جداکردن رکوردهای واقعی Django از دوره‌ها/مربیان نمونهٔ Preview.
4. اتصال وبلاگ Preview به صفحات واقعی `/blog/` و `/blog/<slug>/` بدون استفاده از mock JSON.
5. تعیین تکلیف تاتامی‌پدیا، مربی آنلاین، AI، نقشه، داشبوردها و قابلیت‌های فاقد قرارداد.
6. پس از تثبیت رفتار، شکستن پل Django به اجزای کوچک‌تر با تست رگرسیون.

## ۸. دروازهٔ تست و انتشار

- `cd shared && npm test`
- تست‌های متمرکزِ مربوط به صفحه و نقش تغییرکرده.
- `node tests/django-bridge.test.mjs` و `node tests/auth-route-contract.test.mjs` در پوشهٔ `shared/`.
- `node build.js` و بررسی خروجی `dist/`.
- workflow قرارداد Django باید با revision ثابت و فعلی بک‌اند اجرا شود.
- بستهٔ cPanel باید مانیفست، اندازه و SHA256 را پاس کند؛ `install.py --check` فقط بررسی می‌کند و چیزی نصب نمی‌کند.
- انتشار روی cPanel دستی و با تأیید صاحب سایت است. موفقیت CI به‌معنی نصب یا انتشار نیست.

**خط قرمز انتشار:** هیچ تغییری در DB، migration، `.env`، کد Python، WSGI، `.htaccess`، Passenger یا static root سرور از این مسیر فرانت‌اند انجام نمی‌شود.
